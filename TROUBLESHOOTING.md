# Troubleshooting Notes — terraformdriftmonitor

Known gotchas that aren't obvious from the code alone. Check here first
if something behaves unexpectedly.

---

## Standing rule: tag values use letters, numbers, spaces, hyphens ONLY

This isn't a gotcha to debug — it's a rule to follow so the gotcha
never happens. Hit this same underlying problem **three separate
times** across different AWS services before settling on one simple
rule instead of three service-specific exceptions:

- An em-dash in an IAM tag value broke a real `terraform apply`
  (IAM tag values only allow `[\p{L}\p{Z}\p{N}_.:/=+\-@]*` — no em-dash)
- A comma in an S3 bucket tag value broke a different `terraform apply`
  (S3's allowed set is stricter than IAM's and explicitly excludes commas)
- A missing validation block meant nothing caught either of these
  before a real `apply` failed partway through

**Each service has a slightly different allowed character set.**
Researching and memorizing each one individually (as happened here,
twice) is the slow, error-prone way to avoid this. The fast way:
**never put anything in a tag value except letters, numbers, spaces,
and hyphens.** No em-dashes, no commas, no slashes, no colons, no
underscores, no periods — even where a specific service would
technically allow them. This is more restrictive than strictly
necessary for any single service, but it means never needing to check
again, for any current or future AWS resource type this project tags.

If you're adding a new tagged resource anywhere in this project,
sanity-check its tag values against this rule before running `apply` —
don't wait for the error to teach you which characters that particular
service rejects.

## "Bucket not found" or "Access denied" after touching Terraform state

**Cause:** The deployments bucket name is generated by `random_id` in
`terraform/bootstrap/main.tf`. This value is generated **once** on the
first `terraform apply` and persisted in the state file. It does **not**
regenerate on subsequent applies — that would break everything that
references the bucket name.

**However**, if the state file is ever lost, corrupted, or someone runs:
```bash
terraform state rm random_id.deployments_suffix
```

...the next `terraform apply` will generate a **brand new random suffix**,
which means:

- A **new** S3 bucket gets created with a different name
- The **old** bucket still exists in AWS, now orphaned and unreferenced
- Anything pointing at the old bucket name (IAM policies in this same
  Terraform root will update automatically, but **GitHub Actions
  secrets/variables that reference the bucket name manually will not**
  — they'll still point at the old, now-orphaned bucket)

**If you hit a confusing bucket permission error after any state file
weirdness, check this first.** It might not be a permissions bug —
it might be a brand new bucket that the rest of your config doesn't
know about yet.

**Fix:**
1. Restore the correct state file from a backup, or
2. If using a remote backend with versioning (recommended for any real
   use), restore the previous state version, or
3. If the new bucket is genuinely intended, update every place that
   references the bucket name manually (GitHub Actions variables, any
   hardcoded references) to the new name

**Prevention:** Use a remote backend (S3 + state locking via DynamoDB
or native S3 locking) with versioning enabled, rather than local state
files, for any environment beyond initial learning/testing.

## OIDC trust policy "not authorized to perform sts:AssumeRoleWithWebIdentity"

**Cause:** Usually one of:
- The workflow is running from a branch/PR that doesn't match the
  `sub` claim condition in the trust policy
- The repo name or org name in `terraform/bootstrap/variables.tf`
  doesn't exactly match the actual GitHub repo (case-sensitive)
- The OIDC provider thumbprint is stale (rare now — we use the dynamic
  `tls_certificate` data source specifically to avoid this, but if you
  ever hardcode a thumbprint instead, this is the first thing to check)

**Fix:** Check the exact `sub` claim being sent — add a debug step to
the workflow:
```yaml
- name: Debug OIDC claims
  run: |
    echo "Repository: ${{ github.repository }}"
    echo "Ref: ${{ github.ref }}"
```
Compare against the `StringLike` condition in
`terraform/bootstrap/main.tf`.

## Preflight fails with "role has been tampered with" but nothing was changed

**Cause:** The role integrity hash in SSM is out of sync with the
actual role — usually because `terraform/bootstrap/` was applied
manually but the hash update step wasn't run, or the hash was
generated against a different version of the role policy.

**Fix:** Re-run `terraform apply` in `terraform/bootstrap/` — the hash
should update as part of the apply. If it still fails, manually compare
the policy JSON via:
```bash
aws iam list-role-policies --role-name tfdriftmonitor-github-deploy
aws iam get-role-policy --role-name tfdriftmonitor-github-deploy --policy-name POLICY_NAME
```
against what's expected, then regenerate the SSM hash.

## Pipeline fails partway through with expired/invalid credentials

**Cause:** The deploy role's `max_session_duration` is set to 3600 seconds
(1 hour) in `terraform/bootstrap/main.tf`. This is intentional — a short
session window limits how long stolen credentials would be useful if
ever leaked from a running job. For this project's pipeline (preflight,
security scans, terraform plan/apply, package, deploy) that's normally
plenty of time.

**However**, if you expand the pipeline later — more security scanners,
a large monorepo scan, slow integration tests, or a Terraform plan
against a much bigger infrastructure footprint — a single job can
exceed 1 hour. When the OIDC-issued credentials expire mid-job, AWS CLI
and SDK calls start failing with `ExpiredToken` or `InvalidClientTokenId`
errors that can look unrelated to the real cause.

**Fix options, in order of preference:**
1. Split the job into smaller jobs that each re-authenticate via OIDC
   (each job gets a fresh 1-hour window) — best practice, keeps the
   short-session security benefit
2. Increase `max_session_duration` in `terraform/bootstrap/main.tf`
   (up to AWS's max of 12 hours / 43200 seconds) — only do this if
   splitting genuinely isn't practical, since it weakens the original
   security intent of short-lived credentials
3. Profile the slow step first — sometimes the real fix is making the
   pipeline faster (caching dependencies, parallelizing scans) rather
   than just giving it more time

**If you do increase it**, re-run `terraform apply` in
`terraform/bootstrap/` and note that the role integrity hash will
change as a result — this is expected, not a tamper event, since the
change came through Terraform itself.

## `git push` rejected with "would publish a private email address"

**Cause:** Your GitHub account has "Keep my email address private"
enabled (default for new accounts), but your local git config is set
to your real email address. GitHub blocks the push rather than expose it.

**Fix — use GitHub's no-reply address instead of your real email:**

1. Find your no-reply address: https://github.com/settings/emails
   Look for something like `12345678+yourusername@users.noreply.github.com`

2. Set it as your git email going forward:
   ```bash
   git config --global user.email "12345678+yourusername@users.noreply.github.com"
   ```

3. **If a commit was already made before fixing the config**, the
   config change alone won't fix that specific commit — it already
   has your real email baked in. Rewrite just that commit's author info:
   ```bash
   git commit --amend --reset-author --no-edit
   git push
   ```

**Why this is the better fix** (vs. the alternative GitHub offers, which
is just making your email public): keeps your real address out of
public commit history permanently, which matters for any repo —
doubly so for a security-focused one.

## macOS hides dotfiles/folders (`.github`, `.gitignore`, `.git`) in Finder

**Not a bug** — this is intentional macOS/Finder behavior, not specific
to this project. Affects anything starting with a `.`.

**Two ways to work around it:**

1. **Use the terminal** (recommended — more precise, avoids drag-and-drop
   mistakes with security-sensitive files):
   ```bash
   mv ~/Downloads/somefile.yml ~/terraformdriftmonitor/.github/workflows/somefile.yml
   ls -la ~/terraformdriftmonitor/.github  # confirms it landed
   ```

2. **Make Finder show hidden files permanently:**
   ```bash
   defaults write com.apple.finder AppleShowAllFiles YES
   killall Finder
   ```
   To reverse:
   ```bash
   defaults write com.apple.finder AppleShowAllFiles NO
   killall Finder
   ```

## A version check run takes ~20+ seconds longer than expected

**Not a bug** — `python-hcl2`'s underlying `lark` parser appears to
compile its grammar lazily on the *first* actual call to `hcl2.loads()`
within a running process, not at module import time. That one-time
compilation can take 15-20+ seconds. It happens once per warm Lambda
container's lifetime (subsequent `.loads()` calls in the same container,
even across multiple files or multiple repos in the same invocation,
reuse whatever lark already compiled in memory) — it is not multiplied
per file or per repo. Well within the default 300-second Lambda timeout.
If you see one run noticeably slower than the next, this is the likely
explanation, not a sign something is broken.

## "tfdriftmonitor-not-invoked" alarm fires immediately after first deploy

**Not a bug, and not a sign anything is wrong** — this is an
unavoidable cold-start artifact of the dead-man's-switch design,
expected on any fresh deployment.

The alarm checks "was there at least 1 invocation in each of the last
7 daily periods." On a brand-new Lambda, there's no invocation history
for the days *before* the function existed — those empty historical
periods are deliberately treated as `breaching` (via
`treat_missing_data = "breaching"`), specifically so a real EventBridge
failure can't hide behind "insufficient data" instead of triggering a
real alert. The trade-off: a function with less than 7 days of history
will essentially always trip this alarm once, immediately, regardless
of whether anything is actually broken.

**No action needed.** The alarm self-clears once a full real 7-day
trailing window of normal scheduled/manual activity accumulates. If it
fires again *after* you have a genuine week of consistent invocation
history, that's the signal to actually investigate.
